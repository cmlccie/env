## Shell Startup

`zsh` is the interactive shell on every platform. `bash` is kept deliberately minimal: it
exists for scripts and for AI coding agents, which need `PATH` and tool environment but are
hindered by interactive UX (prompts, completions, aliases, shell integrations).

Shared configuration lives in `home/.config/shell/`, one concern per file:

| File             | Sourced by          | Concern                                |
| ---------------- | ------------------- | -------------------------------------- |
| `lib.sh`         | `env.sh`            | POSIX helper functions                 |
| `paths.sh`       | `env.sh`            | `PATH` construction                    |
| `env.sh`         | **every shell**     | environment variables; the entry point |
| `interactive.sh` | `.zshrc`, `.bashrc` | interactive-only variables             |
| `aliases.sh`     | `interactive.sh`    | aliases                                |

```text
.zshenv / .zprofile / .bash_profile / .bashrc / .profile / $BASH_ENV
        └── env.sh ──┬── lib.sh      (helpers; loads above the re-entry guard)
                     └── paths.sh    (PATH; loads below it)

.zshrc / .bashrc
        └── interactive.sh ── aliases.sh
```

Rules worth knowing before editing these files:

- **`env.sh` must stay silent and side-effect free.** It is reached by `$BASH_ENV`, so every
  non-interactive `bash` on the machine reads it. Anything that prints breaks `scp`, `rsync`,
  and `git` over SSH; anything slow is paid by every script.
- **Aliases never go in `env.sh`.** zsh expands aliases in non-interactive shells, so an alias
  reachable from there would silently shadow a binary an agent invokes.
- **`lib.sh` loads above the `__SHELL_ENV` guard, `paths.sh` below it.** Environment variables
  cross `fork+exec`; shell functions do not. A nested shell must redefine the helpers but
  should inherit `PATH` rather than rebuild it.
- **Login files (`.zprofile`, `.bash_profile`, `.profile`) `unset __SHELL_ENV` first.** macOS
  runs `/usr/libexec/path_helper` between `.zshenv` and `.zprofile`, which hoists `/usr/bin`
  ahead of Homebrew; clearing the guard re-applies the correct order.
- **A variable that locates a bin directory** (`HOMEBREW_PREFIX`, `GOPATH`, `CARGO_HOME`,
  `NVM_DIR`) belongs in `paths.sh` beside the `path_prepend` that uses it.
- **Completions are generated by `./upgrade-packages.sh completions`**, never at shell startup.

## Python Toolchain

`uv` manages interpreters, project environments, and command-line tools. There is no
system-wide Python environment and no `pyenv`: the macOS system interpreter is never used
for project work, and packages that used to be installed globally now live either in a
project's own `uv` venv or in an isolated `uv tool` environment.

`python/uv-tools.txt` is the cross-machine manifest of command-line tools, in the same
spirit as `platforms/macos/Brewfile`. Each line is passed through to `uv tool install`, so
extras and plugins are declared inline:

```text
ipython
mypy
ruff
poetry --with poetry-plugin-export
```

`./upgrade-packages.sh python` installs anything missing (already-installed tools are a
no-op, so it doubles as the bootstrap), then runs `uv tool upgrade --all` and
`uv python upgrade`. Tool binaries land in `~/.local/bin`, which `paths.sh` already
prepends -- no shims, no shell hook, nothing at startup.

Poetry is one of those tools. It is kept so that Python projects predating the move to `uv`
stay maintainable; it manages those projects exactly as before and has no role in this
repository's own package management.

Libraries never go in `uv-tools.txt`. Every project gets its own `uv`-managed virtual
environment.

## Documentation for AI Agents

`AGENTS.md` at the repository root is the instruction file for AI coding agents, following
the cross-agent [AGENTS.md](https://agents.md/) convention. `.claude/CLAUDE.md` is a symlink
to it, so Claude Code and every other agent read one source of truth.

Do not confuse it with `home/.config/agents/AGENTS.md`, which shares the filename but is the
*global* instruction file deployed to `~/.config/agents/AGENTS.md` and applies on every
project on the machine.

## Principles and Methods

- Use _this_ git repository to keep common shell configurations and package lists synchronized between development environments.
  - Configurations and scripts should be portable!
    - Don't use absolute path references.
    - Don't assume that a tool is installed; check if it is.
- Don't use the macOS system Python interpreter. Use `uv` to manage installed interpreters.
- Keep system-level package installations to a minimum.
- Create project-specific virtual environments for every project. Use `uv` to manage project dependencies and the associated environment.
- If project artifacts will be deployed in a Docker container, do the project development using the container environment.
- Remember the _wisdom_ in [PEP20](https://www.python.org/dev/peps/pep-0020/) (even when coding in another language).
- _Almost always_ follow [PEP8](https://www.python.org/dev/peps/pep-0008/).
