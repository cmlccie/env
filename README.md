## Shell Startup

`zsh` is the interactive shell on every platform. `bash` is kept deliberately minimal: it
exists for scripts and for AI coding agents, which need `PATH` and tool environment but are
hindered by interactive UX (prompts, completions, aliases, shell integrations).

Shared configuration lives in `home/.config/shell/`, one concern per file:

| File             | Sourced by          | Concern                                |
| ---------------- | ------------------- | -------------------------------------- |
| `lib.sh`         | `env.sh`            | POSIX helper functions                 |
| `paths.sh`       | `env.sh`            | `PATH` construction                    |
| `env.sh`         | **every shell**     | environment variables; the entry point |
| `interactive.sh` | `.zshrc`, `.bashrc` | interactive-only variables             |
| `aliases.sh`     | `interactive.sh`    | aliases                                |

```text
.zshenv / .zprofile / .bash_profile / .bashrc / .profile / $BASH_ENV
        └── env.sh ──┬── lib.sh      (helpers; loads above the re-entry guard)
                     └── paths.sh    (PATH; loads below it)

.zshrc / .bashrc
        └── interactive.sh ── aliases.sh
```

Rules worth knowing before editing these files:

- **`env.sh` must stay silent and side-effect free.** It is reached by `$BASH_ENV`, so every
  non-interactive `bash` on the machine reads it. Anything that prints breaks `scp`, `rsync`,
  and `git` over SSH; anything slow is paid by every script.
- **Aliases never go in `env.sh`.** zsh expands aliases in non-interactive shells, so an alias
  reachable from there would silently shadow a binary an agent invokes.
- **`lib.sh` loads above the `__SHELL_ENV` guard, `paths.sh` below it.** Environment variables
  cross `fork+exec`; shell functions do not. A nested shell must redefine the helpers but
  should inherit `PATH` rather than rebuild it.
- **Login files (`.zprofile`, `.bash_profile`, `.profile`) `unset __SHELL_ENV` first.** macOS
  runs `/usr/libexec/path_helper` between `.zshenv` and `.zprofile`, which hoists `/usr/bin`
  ahead of Homebrew; clearing the guard re-applies the correct order.
- **A variable that locates a bin directory** (`HOMEBREW_PREFIX`, `GOPATH`, `CARGO_HOME`,
  `NVM_DIR`) belongs in `paths.sh` beside the `path_prepend` that uses it.
- **Completions are generated by `./upgrade-packages.sh completions`**, never at shell startup.
- **The devbox global profile reaches `PATH` by a static `path_prepend` in `paths.sh`**, never
  `eval "$(devbox global shellenv)"`. `paths.sh` is reached through `$BASH_ENV` by every
  non-interactive `bash`, so a fork-per-shell hook would be both slow and a violation of the
  silence rule. `path_prepend`'s directory check makes the line a no-op when devbox is absent.

## Package Management

Three manifests, each owning one thing, and no overlap between them:

| Manifest                   | Manager        | Owns                                       |
| -------------------------- | -------------- | ------------------------------------------ |
| `nix/packages.json`        | `devbox global`| command-line tools, host and agent alike   |
| `platforms/macos/Brewfile` | Homebrew       | macOS GUI applications, fonts, `tetra`     |
| `python/uv-tools.txt`      | `uv`           | Python command-line tools                  |

`nix/packages.json` is the only one of the three a human edits for CLI tools, and it is
split so a single file drives two environments:

```text
nix/packages.json
   |  { "shared": [...], "host_only": [...] }
   |
   +-- shared + host_only  ->  nix/global.json  ->  devbox global    (this machine)
   +-- shared              ->  <project>/.devcontainer/devbox.tools.json  (agent container)
```

`./upgrade-packages.sh nix` renders `nix/global.json` and applies it with
`devbox global pull --force`, which makes the file **authoritative**: a package deleted from
`nix/packages.json` leaves the profile. Do not use `devbox global add` -- it only ever adds,
so the manifest and the installed profile would drift apart. `sandcat-sync <project>` writes
the `shared` half into a project's container manifest.

Lock-step between the two environments is a property of the version strings. Sandcat's
`devbox.tools.json` is a bare `{"packages": [...]}` fragment with no nixpkgs revision key, so
`name@version` is the only pin available; an `@latest` entry resolves independently on each
side and will drift.

Homebrew keeps three formulae on purpose. `tetra` because the nixpkgs `tetragon` package is
Linux-only and builds from source; `pinentry-mac` because it drives a macOS GUI prompt; and
`chipmk/tap/docker-mac-net-connect` because it routes Docker Desktop traffic. Everything else
under `brew` is a GUI cask.

Bootstrapping a new machine:

```sh
curl -fsSL https://get.jetify.com/devbox | bash   # installs Nix too; do this interactively
./setup-home.py
./upgrade-packages.sh
home/.local/bin/update-shell.sh
```

On a machine where the GUI applications were installed by hand rather than by Homebrew,
adopt them once before the first `brew bundle`, or it will refuse to overwrite the existing
app bundles and abort the run:

```sh
brew install --cask --adopt docker-desktop visual-studio-code iterm2
```

`nvm`, `oh-my-zsh`, and `powerlevel10k` stay on their own installers. `nvm` is not packaged
in nixpkgs in any usable form -- it is a sourced shell function, not a binary -- and the other
two need writable trees (`~/.oh-my-zsh/custom/plugins`, `~/.oh-my-zsh/completions`) that the
read-only Nix store cannot provide.

## Python Toolchain

`uv` manages interpreters, project environments, and command-line tools. There is no
system-wide Python environment and no `pyenv`: the macOS system interpreter is never used
for project work, and packages that used to be installed globally now live either in a
project's own `uv` venv or in an isolated `uv tool` environment.

`python/uv-tools.txt` is the cross-machine manifest of command-line tools, in the same
spirit as `platforms/macos/Brewfile`. Each line is passed through to `uv tool install`, so
extras and plugins are declared inline:

```text
ipython
mypy
ruff
poetry --with poetry-plugin-export
```

`./upgrade-packages.sh python` installs anything missing (already-installed tools are a
no-op, so it doubles as the bootstrap), then runs `uv tool upgrade --all` and
`uv python upgrade`. Tool binaries land in `~/.local/bin`, which `paths.sh` already
prepends -- no shims, no shell hook, nothing at startup.

Poetry is one of those tools. It is kept so that Python projects predating the move to `uv`
stay maintainable; it manages those projects exactly as before and has no role in this
repository's own package management.

Libraries never go in `uv-tools.txt`. Every project gets its own `uv`-managed virtual
environment.

## Agent Sandbox

AI coding agents run in a [sandcat](https://github.com/VirtusLab/sandcat) container: a dev
container whose every packet is routed through a transparent mitmproxy, with a default-deny
allowlist and secrets substituted at the proxy rather than handed to the container.

Set one up per project:

```sh
cd <project>
SANDCAT_MOUNT_CLAUDE_CONFIG=false sandcat init --agent claude --ide vscode
sandcat-sync .
sandcat run --build
```

The container reproduces this environment rather than approximating it. `Dockerfile.app`
clones this repository to `/opt/env` and runs `setup-home.py`, so the agent gets the real
shell load graph, the aliases, `GIT_EDITOR=false`, and `~/.local/bin`. That clone is also
what makes `~/.claude/CLAUDE.md`'s `@~/.config/agents/AGENTS.md` import resolve: sandcat's
default mounts cover `~/.claude/CLAUDE.md` but not `~/.config/agents/`, which is why the
mounts are disabled with `SANDCAT_MOUNT_CLAUDE_CONFIG=false`.

Three deliberate asymmetries between the container and this machine:

- **The agent commits but never pushes.** No `GITHUB_TOKEN` and no SSH or GPG agent
  forwarding. Sandcat's network rules match host and method but have no path field, so
  `git push` cannot be denied by rule -- the absence of a credential is the enforcement.
- **`~/.claude/settings.json` is deleted in the container.** The machine-wide copy enables
  Claude Code's own bubblewrap sandbox, which cannot start in a dev container. Sandcat's
  proxy and container boundary are the isolation there.
- **`op` runs against a scoped service-account token.** The token is real, not a proxy
  placeholder, because `op` parses it client-side before making any request. The service
  account is scoped to a subset of vaults, and that subset is the entire boundary -- keep
  it minimal.

Sandcat installs [rtk](https://github.com/VirtusLab/rtk) into the container by default and
patches Claude's config with a token-compression hook. That is one more tool than this
machine has; it is kept deliberately. Set `SANDCAT_RTK=false` at `sandcat init` to opt out.

The clone lives in `/opt` rather than under `$HOME` because `/home/vscode` is a named volume
that masks anything the image writes there. As a result, changing the *content* of a dotfile
reaches the container on a plain `sandcat run --build`; *adding or removing* a file under
`home/` needs `sandcat compose down -v`, which also clears the agent's credentials.

## Documentation for AI Agents

`AGENTS.md` at the repository root is the instruction file for AI coding agents, following
the cross-agent [AGENTS.md](https://agents.md/) convention. `.claude/CLAUDE.md` is a symlink
to it, so Claude Code and every other agent read one source of truth.

Do not confuse it with `home/.config/agents/AGENTS.md`, which shares the filename but is the
*global* instruction file deployed to `~/.config/agents/AGENTS.md` and applies on every
project on the machine.

## Principles and Methods

- Use _this_ git repository to keep common shell configurations and package lists synchronized between development environments.
  - Configurations and scripts should be portable!
    - Don't use absolute path references.
    - Don't assume that a tool is installed; check if it is.
- Don't use the macOS system Python interpreter. Use `uv` to manage installed interpreters.
- Keep system-level package installations to a minimum.
- Create project-specific virtual environments for every project. Use `uv` to manage project dependencies and the associated environment.
- If project artifacts will be deployed in a Docker container, do the project development using the container environment.
- Remember the _wisdom_ in [PEP20](https://www.python.org/dev/peps/pep-0020/) (even when coding in another language).
- _Almost always_ follow [PEP8](https://www.python.org/dev/peps/pep-0008/).
